Objects are structures that allow you to store data (records, attributes, and values) specific to an organization. Twenty provides both standard and custom objects.

Standard objects are in-built objects with a set of attributes available for all users. Examples of standard objects in Twenty include Company and Person. Standard objects have standard fields that are also available for all Twenty users, like Company.displayName.

Custom objects are objects that you can create to store information that is unique to your organization. They are not built-in; members of your workspace can create and customize custom objects to hold information that standard objects aren't suitable for.


## High-level architecture

Twenty has transitioned to a **Firebase-native architecture**. Custom object definitions are no longer stored in relational database tables. Instead, they are managed through a **JSON-schema driven metadata system** backed by Firestore.

## How it works: JSON-Schema Metadata

Custom objects are defined by JSON schemas stored in the `_metadata` collection within Firestore. This system determines the shape, name, and validation rules for each object.

- **Metadata Collection**: Firestore collection containing JSON schemas for all workspace objects.
- **Dynamic Validation**: The backend utilizes [Ajv](https://ajv.js.org/) to validate incoming data against these schemas in real-time.
- **GraphQL Generation**: Twenty's engine dynamically generates a GraphQL schema based on these JSON definitions, enabling a type-safe API for custom data.

### Adding a Custom Object
To add a custom object, a workspace member interacts with the metadata service. This service:
1. Validates the proposed object structure.
2. Persists the new JSON schema to the `_metadata` collection.
3. Triggers a real-time update that refreshes the dynamic GraphQL schema across all server instances.

### Fetching and Modifying Data
When a client queries the `/graphql` or `/rest` endpoints:
1. The request is intercepted by the workspace-specific resolver.
2. The engine translates the request into a Firestore query.
3. Data is validated against the corresponding JSON schema before being returned to the client or persisted to the database.
